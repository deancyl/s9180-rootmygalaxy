### 2.1 频次与分布（本日志周期 11-04 18:00 → 11-05 14:43）

- 合计 **76 次 / 约 21 小时 ≈ 3.6 次/小时**，**全天连续分布**（含白天与深夜），不是偶发。
- 深夜（00–06）异常信号 `frc3_night_hit = 23`；1h 内 ≥6 次进入风暴态 **12 次**（06:45–06:58、08:01–08:04、09:17–09:18 等密集簇）。
- 每次护航提权 **59–79 个 camera provider 线程**（nice=-8），15s 或条件消失后还原。
- 14:39 采样时 `mWakefulness=Dozing`（息屏），14:38:36 刚发生借相机；15:29 采样时 `Awake` + 微信前台，FaceService 仍在 `semSessionClose`。

### 2.2 调用者归因（logcat 实证，15:29:33 窗口）

```
D/KeyguardFace(30602): canFaceAuthRun / canFaceDetectRun（高频反复判定）
I/FaceService(28875): semSessionClose called from pid=30602, userId: 0
I/sec_fr_NativeFaceService(1783): FaceService::unloadTA / deinitialize
D/BiometricService(28875): resetLockout / canAuthenticate (Modality: 1)
I/CameraService(28463): onUidStateChanged: uid=10335（微信进程状态变化，非相机打开）
```

- **发起者 = SystemUI/Keyguard 的人脸识别链路**（pid 30602 `KeyguardFace` → `FaceService` → face HAL pid 1783 → 借 camera provider）。
- 这是**系统级生物识别服务**，不受「后台应用相机权限」约束 → 解释了为何用户「后台一般不允许相机」但息屏/后台仍高频发生。
- **与用户场景对照**：拍照与美团扫码是前台瞬时、低频，无法解释 76 次/21h 且息屏发生 → **不是主因**；用户所说的「AOD 人脸」方向得到实证，且更准确地说是 **Keyguard/FaceService 人脸认证链路（含 AOD/锁屏/解锁态）**。
- **智能锁 / 眼镜**：本轮 logcat 未观测到相关调用者；不排除偶发或短时窗口，列为后续采样项，不做结论。

### 2.3 与系统压力的时序

- 借相机事件与灾难级换页交替/伴生：11:56 41.9万/60s、12:03 20.7万、12:09 30.5万、12:48 38.8万、12:53 **97.9万**、12:56 60.1万、14:39 51.0万、15:07 **89.6万**/60s。
- 14:00:50 `mem_forecast avail 2.20GB / swap 7.81GB`；09:16 曾发生 HeapFull 496MB OOM 软重启。
- 时序上伴生 ≠ 已证因果；需阶段 B 的「借相机 → 堆斜率」定量关联（见 §4）。
- HAL 层：dropbox 22 个 tombstone 中 **20 个 camera.provider-service_64**、2 个 thermal@1.0-service（含 09:16:02 `CameraThermistor::update_temperature` 空指针）→ 相机 HAL 反复崩溃是长期事实，与借相机链路同域。

## 3. 阶段 A 结论

1. **借相机是系统级常态链路，不是异常后台相机调用**：KeyguardFace/FaceService 人脸认证，全天（含息屏）周期性初始化/反初始化 face HAL 并借 camera provider。
2. 「根治借相机」**不能靠禁止/拦截**（会破坏人脸解锁，且 hook/杀冻已明确否决）；方向应转为：
   - **降低其系统代价**（护航期 CPU/换页争用、provider 线程提权规模与频次）；
   - **提前预警联动**（风暴态 1h≥6 次时提前触发堆探测/GC 加速，不等 480MB）；
   - **用户侧可选配置**：如用户愿意牺牲部分人脸便利，可在系统设置关闭「人脸解锁 / AOD 人脸相关」后对比频次（**本轮不改任何系统设置**）。
3. 智能锁/眼镜未观测到，保持开放。
