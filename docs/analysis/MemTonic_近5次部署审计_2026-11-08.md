# MemTonic 近 5 次部署审计 · 与 NoActive 协同评估（2026-11-08）

## 一、结论摘要（TL;DR）

| 问题 | 结论 |
|---|---|
| 模块是否在持续优化？ | **是，但优化的是"模块自身开销"，不是"设备内存问题"**。扫描耗时 190ms 稳定、模块 CPU 0.75% 单核、RSS 13MB，都属于优秀水平；但 19 天堆水位没有任何系统性下降。 |
| NoActive 是否生效？ | **生效**。LSPosed 日志显示它每次 system_server 重启后都会重新注入（最近一次 11-07 23:03:31，软重启后 6 秒）。`pidof` 为空是正常的——它是纯 hook 模块，不常驻进程。 |
| NoActive + MemTonic 是否解决了以往的痛点？ | **没有。** 设备 12GB 物理内存已用 99.3%（free 仅 79MB）、swap 已用 5.5GB、CPU PSI 38%、内存碎片化 compaction 失败率 94.8%。四起 HeapFull OOM 一起都没被阻止。两个模块都在"减缓体感"，没有改变"容量不足"这个根因。 |
| 模块最大价值在哪？ | ① 压力下的**即时护航**（37 小时 821 次，固定 15s 脉冲）；② **取证**（628 个堆快照覆盖 19 天，四起 OOM 都有现场）；③ 相机借调 / 蓝牙链路的精准提权。**不在"防 OOM"**。 |
| 最该改的三件事 | ① 堆探测 `dumpsys meminfo` 是**唯一的 cpu_scan 尖峰源**（最高 9220ms），需条件化；② 护航 821 次/37h 无续期，renice 频繁；③ 堆快照 275 个/天，超设计 2 倍，可限流。 |

## 三、模块自身是否在持续优化（分维度）

### 3.1 扫描性能：稳定，尖峰另有原因

|---|---|---|---|---|---|

| 11-07 | 1055 | 50 | 190 | 230 | **9220** |
| 11-08（v1.13.14） | 219 | 60 | 190 | 230 | **410** |

**尖峰全部来自 `dumpsys meminfo`，不是扫描**。14 次 >1000ms 的尖峰，上下文全部紧邻 `act=ss_heap_probe`（如 11-07 10:03:00 probe 412200KB → 10:03:10 扫描 9220ms），或紧邻 63 线程 `flush_guard_on/off`。

> v1.13.14 期 0 尖峰，**不是因为优化了探测，而是因为堆只有 236MB、没到 400MB 落盘线，探测根本没触发**。一旦堆再上去，尖峰会回来。这一点必须说清楚，不能算 v1.13.14 的功劳。

## 四、NoActive 验证与协同评估

### 4.1 它确实在工作

```
[2026-11-02T19:34:00] (system)[cn.myflv.noactive,XposedBridge,...] NoActive运行环境正常
[2026-11-07T23:03:31] (system)[cn.myflv.noactive,XposedBridge,...] NoActive运行环境正常
```

- 注入目标是 **system_server**（`(system)` 前缀），11-07 23:03 软重启后 **6 秒**重新注入 ✓
- `versionName=Pro`、`stopped=true`（app 从未被手动打开，正常）、未禁用、未挂起
- `pidof` 为空 **不是故障**：纯 hook 模块不需要常驻进程
- 当前 **102 个进程处于 frozen 状态**

### 4.2 但协同并没有解决容量问题

| 指标 | 当前值 | 含义 |
|---|---|---|
| MemTotal / MemFree | 11044MB / **79MB** | 物理内存 **99.3% 用满** |
| Swap used | **5559MB** / 12287MB | 靠 swap 撑住，累计写出 1.18TB |
| CPU PSI avg10 | **38.19%** | CPU 因等待而停摆的时间占比很高 |
| `pgmajfault` | 8.46 亿 | 累计主缺页，换页风暴的量化根因 |
| `compact_stall / fail` | 318377 / 301782 | **94.8% 的内存压缩失败**（碎片化严重） |
| zram 压缩率 | 5.83GB → 2.28GB（2.56x） | swap 已高效压缩，仍不够 |

**结论**：NoActive（冻结后台）+ MemTonic（护航 + 泄压）合起来做的是"**在超额负载下维持体感**"，而不是"消除超额负载"。设备实际内存需求 > 12GB 物理 + 5.6GB swap，这是**容量级问题**，两个模块都碰不到。

### 4.3 一个被忽略的放大器

```
max_cached_processes=1030
mCustomizedMaxCachedProcesses=1024
CUR_MAX_CACHED_PROCESSES=1030
```

- 来源已查清：`settings activity_manager_constants=null`、`device_config=null`、props 无相关项 → 这是**三星 ROM 的定制默认值**（`mCustomized*` 前缀），**不是 MemTonic / NoActive 改的**。
- 影响：系统允许缓存 **1024 个进程**不回收，远高于 AOSP 默认（通常 32–64）。这意味着内存紧张时，系统更倾向"压 swap"而不是"杀缓存"，直接推高 swap 与 majflt —— 与观测到的 5.5GB swap、8.46 亿 majfault 完全吻合。
- 这不是"模块的错"，但是**当前痛点的结构性放大器**，值得让用户知情（见方案 C-1）。

## 五、模块启用 / 不启用，各会引发什么问题

### 5.1 启用时（当前状态）

**收益（有数据）**
- 前台护航 828 次/37h：压力下对主线程与渲染线程提权 15s，直接改善前台流畅
- 相机借调 268 次：face-service 借相机时提权 63 个 provider 线程，减少相机启动延迟
- 蓝牙 LE 护航 77 次：RayNeo GATT 压力期提权
- 取证：628 个堆快照 + 四起 OOM 现场；本次审计的所有结论都建立在它之上
- 内存整理 21 次、GC 加速 4 次

**代价（有数据）**
- 扫描：每 60s 一次，190ms → 约 **0.3% 单核**
- 堆探测：98 次/天 × 平均 2–3s ≈ **0.3–0.5% 单核**，且是**唯一的 9s 级尖峰源**
- 日志：cpu_scan 占日志 32%（1779/5583 行），37 小时滚满 526KB
- 快照：275 个/天、628 个 inode、占用 4MB
- 调度抖动：821 次提权/还原，涉及前台与渲染线程

**风险（潜在）**
- `drop_caches`（v1.13.14 新增）在高压下每小时最多 6 次，可能带来 IO 抖动——**尚未实弹验证**
- 护航把前台线程提权，极端情况下会挤压 GC 线程（已有 `cpu_psi≥35%` 退避缓解，但非硬隔离）

### 5.2 不启用时

**会失去**
- 前台护航 → 压力期前台卡顿增加（**无法量化，因为没有对照实验数据**，只能说方向明确）
- 相机借调提权 → 相机启动/预览可能变慢（回到 v1.11 之前的状态）
- 蓝牙 LE 护航 → RayNeo 断连重连体验可能变差
- 全部取证 → 下次 OOM 没有现场，无法归因
- WebUI 可视化

**不会失去（重要）**
- **OOM 防护：本来就没防住**（四起零阻止），禁用不会让 OOM 变多
- 堆水位：19 天趋势与模块开关无相关
- 换页风暴：模块只观测不干预（`paging_storm` 只落 flag）

**底线风险**
- 不启用 **更安全**（少一个 root 级调度干预者）
- 但会失去"异常时能自查"的能力

### 5.3 一句话

> 启用 ≈「体感保险 + 黑匣子」，不是「内存扩容」。如果目标是"手机不卡"，值得留；如果目标是"不再 OOM"，它做不到，关掉也一样。

## 七、解决方案（稳妥 / 省电 / 高效，守住底线）

### A. 降本（省电，零功能损失）

| 动作 | 预期收益 | 底线核对 |
|---|---|---|
| **A-1 堆探测条件化**：仅当 `RSS 变化 >30MB` **或** `PSI mem ≥5%` **或** `堆距上次探测上涨 >15MB` 时才 `dumpsys meminfo`；否则用 `/proc/<pid>/status` 的 VmRSS 做代理 | 探测次数从 98/天 降到 10–20/天，**消除 9s 级尖峰**，省 0.3–0.5% 单核 | 只读；不改变判定阈值语义 |
| **A-2 cpu_scan 日志降级**：`done_ms<300` 写 `L=D`（或按 1/10 采样），≥300 才写 `L=S` | 日志量降 ~30%，历史窗口从 37h 扩到 ~50h | 只改日志级别 |
| **A-3 快照限流**：每小时最多 1 个，且自动清理 7 天前文件；危机段（≥470MB）不受限 | 从 275/天 降到 ~24/天，628→~170 文件 | 危机取证不丢 |
| **A-4 护航续期**：压力持续时延长当前护航而非重开；两次护航最小间隔 30s | 821 次降到 ~300 次，renice 调用减 60% | 15s 安全窗保留，续期仍受"条件消失即还原"约束 |

### B. 提效（真正提升 FR-SS 有效性）

| 动作 | 预期收益 | 底线核对 |
|---|---|---|
| **B-1 `drop_caches` 校准**：首次真实触发时记录 `MemFree`/`pgsteal` 前后差值；若 60s 内 free 提升 <200MB，改为只 `echo 1`（仅 page cache）或降频到 30min | 用数据决定是否保留该手段 | 一次性动作，不改持久参数 |
| **B-2 GC 加速下探到 450MB**（当前 460）：与完整泄压链对齐 | 覆盖 450–460MB 震荡段（19 天里高频区间） | 只提权不降级 |
| **B-3 GC 线程绑核失败时降级记录**：`taskset` 失败率需可见 | 确认 -15 + 绑核是否真生效 | 无副作用 |
| **B-4 堆增长速率预测**：连续 3 点斜率 >5MB/10min 时提前进入预备态 | 把窗口再提前 10–20 分钟 | 纯观测 |

### C. 容量层（非模块，需你决策）

| 动作 | 预期收益 | 风险 |
|---|---|---|
| **C-1 降 `max_cached_processes`（1024→256/512）** | 让系统更早回收缓存进程，减少 swap 与 majflt | 应用保活变差（微信/支付宝冷启动变慢）；需改系统设置或模块 hook |
| **C-2 削减常驻大户** | 微信 565MB / systemui 462MB / GMS 428MB / photos 336MB，共约 1.8GB | 影响功能 |
| **C-3 关闭深夜 AOD 人脸** | 减少 FR-C3 借相机 → GC 饿死链条（历史 OOM 主因） | 失去抬腕亮屏人脸解锁 |

> C 类是**唯一能改变"会不会 OOM"的层面**，但都涉及取舍，必须你决定。模块层面（A/B）只能让过程更省、更早、更有据。

### D. 可观测性（让问题一眼可见）

| 动作 | 说明 |
|---|---|
| **D-1 WebUI 增加「整机内存」卡** | 显示 `MemFree / swap used / CPU PSI / compaction 失败率`，与堆并列；当前"堆 223MB 正常"极易误判 |
| **D-2 NoActive 健康检查** | 读 LSPosed verbose 日志最后一条 `NoActive运行环境正常` 的时间；>6h 未更新则在面板提示 |
| **D-3 OOM 风险评分** | 堆水位 + swap 使用 + PSI mem + compaction 失败率 → 低/中/高，配合"今晚可能崩"的直白文案 |

## 八、建议执行顺序

1. **立即（本次可做）**：A-1 探测条件化 + A-2 日志降级 + A-3 快照限流 + A-4 护航续期 —— 纯降本，无策略变更，风险最低。
2. **观察一轮后**：B-1 drop_caches 校准 + B-2 GC 下探 + D-1/D-2/D-3 可观测增强。
3. **需你决策**：C-1 / C-2 / C-3（容量层取舍）。
4. **继续挂起**：FR-RN1 第二轮零 fork（当前旁路态，不影响本次结论）。
