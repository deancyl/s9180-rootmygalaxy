# MemTonic WebUI 四维审查报告（2026-11-05）

> 审查对象：`webroot/index.html` 当前实现（609 行，含 P0/P1/P2 全部改动）＋ 底层 `mt_lib.sh` / `cpu_guard.sh` / `run/` 状态与实弹数据。
> 方法：逐行核对界面可见文案、数据源对接清单、DOM 结构，交叉验证 `collect_stats` 20 字段、106 类日志事件、约 70 个 run 状态文件，以及 16:20 / 15:47 等设备实弹日志。
> 结论口径：**每个维度明确「有/无问题」，列出具体表现（带行号/文案/数值）与可执行的改进方向**。

## 维度 1｜底层功能对接与利用 → **有问题**

**判断**：统计主链已充分对接，但「此刻正在生效的状态」与「用户最能感知的高频事件」两类能力基本未利用。

### 已充分利用（确认无问题的部分）
- `collect_stats` 输出 **20 个字段全部被使用**（state/pid、14 类计数、ssheap、avail_kb、psi_s10/psi_f10），无字段闲置；P1 实弹 5 个新计数与日志直数 **5/5 MATCH**。
- 6 个告警 flag（soft_reboot_advised / boot_context / rollback_warn / paging_storm / rss_warn / reboot_suppressed）全部接入横幅；堆危机链（ss_heap.kb / gc_boost.bak / relief_fail / advise_cnt / forecast / paging_last / last_probe）已渲染；rollback enabling、HAL tombstone、incident 摘要已接入。

### 具体缺口
| # | 未对接的底层能力 | 影响 |
|---|---|---|
| 1 | `storm_active`、`camera_active.flag`、`screenshot_active.flag`、`bt_guard.bak`、`bt2_guard.bak`、`flush_guard.bak`、`camera_vip.bak`、`camera_aff.bak`、`affinity_constrained.lst`、`vk_injected.flag` | 面板只回答「历史上发生过多少次」，不回答「**此刻正在护航/约束什么**」。用户看到 `shield=329` 却不知道当前是否有相机/蓝牙护航在生效；FR-RN1 正在降权时也只有 `rayneo_lines` 一个数字 |
| 2 | `act=deprioritize`（削峰，本周期 **161 次**）、`warn=majflt_disaster`（**41 次**）、`act=frc3_storm_on`（**12 次**）、`event=shield_deactivate`、`act=ss_heap_relief` 成功数 | 这三类恰是用户体感「卡」的直接来源，14 张计数卡里**一张都没有**；「重负载指纹」只统计 `fg_majflt_burst`，与灾难级换页不是一回事 |
| 3 | `mem_forecast.flag` 内容（avail_kb / swap_kb / ts）、`soft_reboot_advised.flag` 的 `java_heap_kb` | 只取 ON/OFF 与 reason，具体数值被丢弃；危机卡显示「预测态 ON」却不显示「可用 2.2GB / swap 7.8GB」 |
| 4 | `dropbox_state.txt`、`cce_ts/cce_size`、`rollback_warned.ts` | 崩溃雷达与回滚征兆的诊断基线不可见（低优先级） |

**改进方向**：① 新增「此刻正在」状态行（读取上述 bak/flag 的存在性，一次 `ls` 即可，零新增唤醒）；② 计数卡补 3 张（削峰 / 灾难换页 / 风暴态），或把它们并入「重负载指纹」的次级说明；③ 危机卡把预测态与建议的数值展示出来；④ 诊断基线放折叠区。

## 维度 4｜稳定性与资源占用/功耗 → **总体无问题（有实测支撑），但有两处可优化**

### 确认达标的部分
- **无新增常驻进程、无新增唤醒**：WebUI 只在页面可见时刷新（`visibilityState !== 'hidden'`），`busy` 单飞防并发。
- **刷新开销减半**：`AUTO_SEC` 15s→30s，每次 refresh 仍 **2 次 `ksu.exec`**（`collect_stats` + 合并后的状态命令），页面可见时约 **4 次 shell/分钟**（原 8 次）。
- **超时与看门狗齐全**：20s / 15s / 60s / 30s 四级超时 + 60s busy 看门狗；exec 桥接兼容老管理器同步调用并清理全局回调。
- **规避已知重操作**：全程无 `dumpsys`（源码 v1.9.7 已证 `dumpsys media.camera` 19038 行 / 521ms 持锁掉帧）；HAL 统计只读文件名不解压。
- **实测**：P0/P1 三次部署 6/7/7 步全绿、零守护重启、`cpu_scan` 170–270ms 无上升；独立旁路验证（flag 双状态、横幅三态）通过；脚本 `sh -n` 全过，单测 138/138。

### 两处具体缺口（本轮已修 / 待优化）
1. **第二次 exec 静默失败**（已修）：原实现 L457 拿到 `r2` 后未检查 errno，若超时/桥接回调丢失，状态区全部显示 `--`、横幅消失，而 `showErr` 只在第一次 exec 检查 → 用户会误以为「一切正常」。现补 `r2.errno !== 0 || parts.length < 11` 时明确提示「状态明细读取不完整…主状态与事件计数仍有效，请点刷新重试」。
2. **单次命令 fork 偏多**（待优化）：合并后的命令约 60 次外部调用（`cat`×12、`grep`×8、`awk`×2、`ls`×5、`head`×7…），其中 4 次 `grep -c` 重复扫同一份 243KB 日志。改进：4 次 grep 合并为 1 次 awk 多模式统计；4 个 pid 文件的 `cat` 改内建 `read`；5 个 incident 的 `head -n 1` 合并为 1 次 awk。预计减少约 12–15 次 fork/refresh，属锦上添花，不影响当前达标结论。
