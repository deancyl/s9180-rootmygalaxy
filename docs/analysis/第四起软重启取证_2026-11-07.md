## 三个真实缺陷（可修复，均在底线内）

### 缺陷 1（核心）：泄压只有 binder 一条路，而 binder 在濒死时必然不可达

`ss_heap_relief` 唯一手段是 `am send-trim-memory`（走 binder 到 system_server）。而堆濒死时 system_server 主线程/binder 池恰好被 GC 与业务压满 → **用 framework 救濒死 framework，自失效**。日志里 22 次尝试、0 次成功、`ss_heap_trim=0` 是铁证。

可行替代（不经过 system_server）：
- `echo 3 > /proc/sys/vm/drop_caches`：内核路径，必定可达；释放页缓存/可回收 slab，间接给 ART 腾出物理页（**一次性动作，非持久参数**）；
- ART GC 守护线程极致提权 + 绑大核：调度路径，不经 binder（现有 gcboost 只提权到 -10，且全天仅 8 次）；
- `am` 失败后 10–20s 内重试 3 次（现有 retry=120s 太长，抓不住短暂可用窗口）。

### 缺陷 2：阈值太晚，有效窗口接近 0

460MB 才开始 trim（且必失败），480MB 才 GC 加速，485MB 告警，496MB OOM 线。本次堆在 450–480MB 高位震荡近 50 分钟，模块始终只在"探测"。

建议前移到：**430MB 进入预备态**（加密探测 + 提前 GC 提权 + drop_caches 小剂量）、450MB 执行完整泄压链、470MB 进入"极限压制"。

### 缺陷 3：判定抖动 + 抑制后无替代动作

- 22:24:49 堆 450MB 时 `ss_heap_recovered` 撤销建议，6 分钟后升到 477MB —— 单点回落即撤销，无法识别"高位震荡 + 缓慢上涨"。
  应改为：连续 3 次探测均 < 440MB 且 30 分钟斜率为负才撤销。
- 22:59:16 `reboot_suppressed.flag`（`source=paging_storm rollback_count=1`）按设计抑制重启建议，但**抑制后没有任何替代动作**。应改为：抑制即进入"极限压制态"（加密探测 + 持续 trim 重试 + drop_caches + GC 绑核），并在面板明示"不能重启，正在极限压制"。

## 修复方案与底线核对

| 动作 | 预期收益 | 底线核对 |
|---|---|---|
| drop_caches 兜底（仅堆 ≥450MB 且 am 失败时，60s 最多 1 次） | 提供一条必定可达的物理页回收路径 | 一次性动作、不动 zram、不改持久内核参数、不杀进程 |
| GC 守护线程极致提权（-10→-15）+ 绑大核 + 持续 120s | 让 GC 真正跑完，而不是被业务线程挤死 | 提权不降级、nice≤-10 的既有线程不动 |
| 阈值前移（430 预备 / 450 完整链 / 470 极限） | 把干预窗口从 ~0 扩大到 30–60 分钟 | 仅改模块自身阈值，不动系统参数 |
| `am` 失败 10–20s 重试 ×3 | 抓住 framework 短暂可用窗口 | 纯读+轻量调用，无副作用 |
| 趋势判定（3 次 <440MB 且斜率为负才撤销） | 消除"建议→撤销→再涨"抖动 | 只改判定，不改阈值语义 |
| 抑制态转"极限压制" | 不能重启时把可做的做到极致 | 仍不代执行重启 |

## 诚实边界（必须说明）

**system_server 的 Java 堆泄漏发生在框架内部，用户态手段无法根治，只能延后与缓解。** 本次 501MB OOM 与 10-22 / 10-25 / 11-05 三起同型（HeapFull 496–501MB @Watchdog），说明存在稳定的内部泄漏源（历史取证指向 face-service/AOD 深夜借相机 → GC 饿死，属系统侧行为）。上述修复能把"几乎无干预"变成"有 30–60 分钟可用窗口 + 一条可达的泄压路径"，但**不能承诺不再发生**。真正根治需要系统侧行为改变（关闭深夜 AOD 人脸/面部服务，或等厂商修复），这属于用户可选的系统设置范畴。
