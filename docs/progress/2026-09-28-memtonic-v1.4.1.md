# MemTonic v1.4.1 开发进度记录（2026-09-28）

> 模块位置：`modules/rmg_memtonic/`（SM-S9180 / dm3q，KernelSU late-load 临时 Root 会话内存维护）
> 本文为脱敏进度记录：不含设备序列号、原始日志与应用清单。

## 一、背景

v1.3.0 引入的"启动风暴护栏"在 2026-09-28 迎来首次**真实 KSU 软重启场景**验证（此前仅有无重启压力测试）。当日发生两次框架重启（01:00 / 07:40），护栏日志完整记录了 16 个风暴窗口的行为，据此完成一轮实证驱动的迭代。

## 二、真实场景验证结论（v1.3.0）

**按预期生效的部分**：
- `storm_start reason=soft_reboot` 正常触发，削峰规模正确（单窗最多 164 个应用进程）
- launcher 让路（renice -4）仅首轮触发——预存进程快照防误削机制工作正常
- 白名单包全程零波及；全部 16 个窗口还原 `failed=0`
- 多数窗口 CPU PSI 回落提前退出（psi_exit=yes）

**发现的问题**：
1. **P2 · 风暴窗口级联重触发**：两次真实软重启共开出 16 个窗口（应为 2 个），同一 system_server PID 连续重开 4-11 轮。根因：`storm_restore_pending` 用全局变量 `cur` 存还原 nice 值，窗口结束覆盖了护栏主循环同名变量，`base=$cur` 存入 nice 值而非 PID → 下轮必判"PID 变化"。级联恰好终止于 `app_renice=0` 的窗口（还原未触碰变量）——与日志逐条吻合，并经隔离沙箱实验实证（空清单/全消失条目保留、活条目覆盖）。
2. **窗口超限**：480s 上限被突破至 619s。归因（扫描慢 vs 还原数千线程 fork+exec）此前无数据支撑。
3. **白名单缺口**：通话录音（com.catalinagroup.*）、syncthing（com.nutomic.*）、记账（com.wangc.*）在窗口内被临时削峰（已还原、failed=0，但违背"不打断后台服务"的设计意图）。
4. 数据口径修正：快照 `swap_kb` 是已用量（SwapTotal−SwapFree）；本机 zram disksize 实为 16GB，无独立 swapfile。PSI 峰值对比（84 vs 91）因采样口径不同仅作方向性参考。

## 三、v1.4.1 变更

| # | 改动 | 性质 |
|---|---|---|
| 1 | `storm_restore_pending` 变量 `cur` → `r_cur`；护栏主循环改为**窗口前先固化 base**（双重保险） | 缺陷修复 |
| 2 | 白名单追加 `com.catalinagroup.` / `com.nutomic.` / `com.wangc.`；新增 `whitelist_skip` 留痕日志（S 级，仅写文件） | 需求修正 + 可观测性 |
| 3 | `storm_end` 增加 `scan_ms` / `restore_ms`（/proc/uptime 毫秒精度），归因窗口超限 | 诊断增强 |

安全边界不变：不杀进程、不冻结、无挂载、无 sepolicy、无 boot 阶段脚本，全部动作限 renice 与 /proc/sys/vm 运行时参数，禁用模块即完全还原。

## 四、验证结果（全部通过）

1. 设备侧 `sh -n` 语法检查 4 个脚本全绿
2. 沙箱回归（隔离 LOG/RLST）：
   - 修复后活条目还原不再污染 `cur`（修复前覆盖为 nice 值，修复后保留原值；`r_cur` 正常赋值，还原逻辑功能不变）
   - 白名单单测：3 个新前缀 HIT、无关包 MISS、旧白名单（GKD）无回归
3. 部署后守护/护栏进程健康，`event=start ver=1.4.0` 入日志，5 文件设备端 md5 与构建端一致
4. 监测脚本 `mt_stormcap.sh` 干跑（test 模式）验证全部采集命令可用：PSI 三通道、MemAvailable、cpu7 频率、zram 压缩率、T0 截断的 am_proc_start 计数、launcher gfxinfo 百分位
